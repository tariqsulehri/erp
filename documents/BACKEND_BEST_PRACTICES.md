# Backend Best Practices

These rules apply to backend APIs, services, validation, posting, security, and error handling.

## API Design

- Use simple route and field names.
- Keep route handlers thin.
- Validate every request on the backend.
- Return clear, user-safe error messages.
- Do not expose raw database errors, stack traces, connection strings, secrets, or SQL messages to users.
- Use consistent response and error shapes.
- Never trust company IDs, user IDs, permissions, or final calculated totals only from the frontend.

## List APIs

- Large list endpoints must support backend pagination.
- Accept `page`, `pageSize`, filters, and sort options where needed.
- Enforce a safe maximum page size, normally 200 records unless there is a specific approved export endpoint.
- Return pagination metadata such as `page`, `pageSize`, `totalRecords`, and `totalPages` when the count is practical.
- Apply filters and sorting in the database query, not after loading records into memory.
- Use stable sorting for transaction lists, such as document date descending plus document number descending.
- Return summary/header rows by default.
- Load line items and heavy related data only through detail endpoints or explicit include options.
- Default transaction list APIs to a practical date range, such as current fiscal year or recent period, when no filters are selected.

## Service Structure

- Put business rules in services, domain helpers, repositories, or focused utility files.
- Keep posting flows explicit and easy to audit.
- Avoid hidden side effects in utility functions.
- Split large services by responsibility when a module grows.
- Use focused helpers for numbering, validation, posting, ledger creation, stock movement, reporting, analytics, settings, and account-code generation.
- Do not duplicate posting, numbering, settings, account-code, date, money, or validation logic across modules.
- Shared backend helpers should have descriptive names and clear inputs/outputs.

## Validation And Business Rules

- Validate required fields, data types, ranges, statuses, dates, and related records.
- Validate configurable values against active company-owned setup records.
- Validate Account Codes using the shared account-code helper.
- Validate fiscal year and accounting period before posting.
- Validate duplicate references where the business rule requires it.
- Validate Cost Center, Project, Department, Approval Status, Auto Reverse Date, and Attachments only when the feature is enabled and persisted.

## Transactions And Posting

- Use database transactions when creating document headers with lines.
- Use database transactions when posting accounting or inventory documents.
- Voucher/document numbers must be generated by the backend, not typed by the frontend.
- Voucher/document numbers should include type, year, and sequence, such as `JV-2026-0001`.
- Draft documents must not affect stock, ledger, cash/bank, customer, or supplier balances.
- Posted documents must not be updated through normal edit endpoints.
- Backend must enforce posted-document locks even if the frontend has a bug.
- Corrections for posted documents must use approved workflows such as Reverse, Void, Return, Debit Note, Credit Note, or Adjustment.
- Posting must protect against two users posting the same document at the same time.
- Lock affected balance rows when stock, supplier balance, customer balance, or cash/bank balance changes.
- Balance updates must happen in the same transaction as ledger or stock movement inserts.
- Every posted accounting document must create a balanced `vouchers` header and related `voucher_lines`.
- `vouchers.total_debit` and `vouchers.total_credit` must be calculated from the voucher lines, not guessed from only the net business amount.
- Business document totals, such as gross amount, discount amount, tax amount, freight amount, other charges, and net amount, must remain on the source document table for audit and print.
- Follow `documents/ACCOUNTING_POSTING_RULES.md` before implementing posting for purchases, sales, returns, bank, cash, or journal modules.
- If a multi-step workflow partly succeeds, return a clear message that tells the frontend exactly what happened.
- Print data should come from backend-approved document data, not unsaved frontend state.

## Database And Prisma Usage

- Follow `documents/DATABASE_DESIGN_RULES.md` for schema design.
- Use Prisma camelCase field names with `@map` for snake_case database columns.
- Use `Decimal` for money, cost, price, quantity, weight, dimensions, tax rates, and discount rates.
- Do not use floating point numbers for financial or inventory quantities.
- Use lookup tables for configurable values.
- Keep database access inside service/repository/helper layers when logic becomes complex.

## Configurable Master Data

- Do not hard-code user-manageable setup values in services, routes, seed-only logic, or validation rules.
- Category, Item Group, Product Type, Brand, Item Size, Origin, UOM, Warehouse, and Location must come from lookup/configuration tables.
- Validate configurable item fields against active records for the same company.
- Brand must be accepted by ID from the Brand table or created through an approved brand setup endpoint.
- Product Catalogue APIs should filter by the same configurable master data used by item entry forms.
- Business-specific item attributes should be handled through configurable item attribute records.

## General Settings

- Store shared company defaults in `general_settings`.
- Backend services should read currency, date, locale, country, and number-format defaults from the company settings service when they need those values.
- Keep company legal/profile fields separate from general application settings.
- Do not hard-code currency symbols, currency position, date formats, locale names, countries, time zones, or separators in backend services, reports, or print data.

## Account Codes

- Backend validation must require 10-digit numeric Account Codes.
- Store Account Codes as text, not numbers.
- Account Codes must follow `MM GG SS PPPP`: Main Category, Group, Sub-Group, Posting Account.
- Customer linked accounts should be created in the `0103010001` to `0103999999` range.
- Supplier linked accounts should be created in the `0201010001` to `0201999999` range.
- Account Code generation should use the shared account-code helper instead of local regex or local arithmetic.

## Inventory

- Every posted inventory transaction must create an `inventory_stock_movements` record.
- `inventory_stock_movements` is the inventory history source of truth.
- `inventory_stock_balances` is a fast current-balance snapshot.
- Stock balance updates must happen in the same transaction as stock movement inserts.
- Reports should read from stock movements and stock balances.

## Audit And Security

- Store who created, updated, posted, approved, reversed, or voided important records.
- Check user permissions on the backend.
- Enforce tenant/company filtering in every company-owned query.
- Never trust company/user IDs only from the frontend.
- Log technical error details on the server.
- Include enough context for support staff without exposing secrets.
